A session is a mechanism for preserving state across otherwise separate interactions.

HTTP is stateless at the protocol level.

One HTTP request does not inherently remember a previous HTTP request.

Applications frequently require continuity.

A user can authenticate during one request.

Later requests can need to know that the same established session is still active.

A shopping cart can persist across requests.

Application preferences can persist across requests.

Temporary workflow state can persist across requests.

Sessions provide one way to maintain this continuity.

Do not confuse a session with authentication.

A session can carry authenticated state.

A session can also exist for an unauthenticated user.

Authentication establishes identity.

A session preserves state.

Authorization determines what the established principal may do.

These are separate responsibilities.

A typical server-side session uses two components:

A session identifier held by the client.

Session state held by the server.

The client sends the session identifier with subsequent requests.

The server uses that identifier to locate the associated session state.

The session identifier is a reference.

It does not need to contain the complete session state.

A simplified flow is:

Client makes request.

Server creates session.

Server generates session identifier.

Server stores session state associated with that identifier.

Server sends the identifier to the client.

Client returns the identifier on later requests.

Server locates the session.

Server validates the session.

Server uses the session state.

Do not trust a session identifier merely because the client supplied one.

The server must determine whether it corresponds to a valid active session.

A session identifier should be unpredictable.

Use a cryptographically secure random source.

Do not generate session identifiers from sequential numbers.

Do not generate session identifiers from user IDs.

Do not generate session identifiers from timestamps.

Do not generate session identifiers from predictable counters.

Do not create a session identifier by concatenating public values.

An attacker who can predict another session identifier can potentially impersonate that session.

Session identifiers are credentials when possession grants access to session state.

Treat them as secrets.

Do not log full session identifiers.

Do not expose them unnecessarily.

Do not place them in URLs unless a protocol explicitly requires it and the risks are understood.

URLs commonly appear in:

Browser history.

Server logs.

Proxy logs.

Analytics systems.

Referrer information.

Screenshots.

Copied links.

Session identifiers should normally be transmitted using mechanisms intended for credentials.

Web applications commonly use cookies.

A cookie is data associated with HTTP requests according to browser cookie rules.

A session cookie can contain a session identifier.

The browser can automatically send the cookie with matching requests.

The cookie itself does not make the session secure.

Its contents and attributes matter.

A session cookie commonly looks conceptually like:

session=<random identifier>

The identifier maps to server-side state.

Do not put plaintext passwords into session cookies.

Do not put private keys into session cookies.

Do not put unnecessary secrets into session cookies.

A cookie can have a Secure attribute.

Secure instructs compatible browsers to send the cookie only over secure transport according to browser rules.

Use Secure for session credentials when HTTPS is required.

Do not expose an authenticated session over plaintext HTTP.

A cookie can have an HttpOnly attribute.

HttpOnly prevents ordinary client-side JavaScript from reading the cookie according to browser behavior.

This can reduce direct session-cookie theft through some script-based attacks.

HttpOnly does not prevent every consequence of cross-site scripting.

A malicious script can potentially perform requests using the user's existing session even when it cannot read the cookie.

Prevent script injection.

Do not treat HttpOnly as complete XSS protection.

A cookie can have a SameSite attribute.

SameSite controls selected cross-site cookie behavior.

Common values include:

Strict.

Lax.

None.

Their exact behavior depends on browser rules and request context.

SameSite can reduce selected cross-site request attacks.

It does not replace complete CSRF analysis.

When SameSite=None is used, browsers commonly require Secure.

Use cookie settings appropriate to the application's actual cross-site requirements.

Do not weaken cookie policy merely to make an integration work without understanding why.

Cookie Domain controls which hosts can receive a cookie according to browser rules.

Avoid unnecessarily broad cookie domains.

A cookie scoped to an entire parent domain can be exposed to more subdomains than required.

Keep session-cookie scope narrow.

Cookie Path restricts cookie transmission according to URL path matching.

Path can reduce unnecessary exposure.

Path is not a strong security boundary against malicious code within the same origin.

Do not rely on cookie Path as the sole authorization mechanism.

Cookie expiration controls persistence.

A session cookie can expire when the browser session ends according to browser behavior.

A persistent cookie can contain an explicit expiration or maximum age.

Cookie persistence and server-side session lifetime are separate.

Deleting the cookie does not necessarily destroy server-side session state.

Expiring server-side session state does not necessarily immediately remove the cookie from the browser.

The server must validate the session on every request where it is used.

If the server-side session is expired, the request must not regain authority merely because the browser still has the identifier.

A session can have a last-activity time.

A session can have an idle expiration time.

Low-risk applications can use different policies.

Destroy or invalidate the authentication state.

Session rotation replaces one session identifier with another.

Rotation is important when authentication state changes.

For example:

User logs in successfully.

Application rotates the session identifier.

Authenticated state becomes associated with the new identifier.

The old identifier is invalidated or otherwise prevented from representing the authenticated session.

This helps prevent session fixation.

Session fixation occurs when an attacker establishes or predicts a session identifier and causes a victim to authenticate using that same identifier.

If the application continues using it after login, the attacker can potentially use the known identifier to access the authenticated session.

Rotate session identifiers when privilege state changes.

Login is a common rotation point.

Privilege elevation can be another rotation point.

Sensitive reauthentication can be another rotation point.

Do not retain an externally supplied or previously exposed identifier after authentication without considering fixation.

Session rotation should preserve only state that is intended to survive.

For example:

Shopping cart contents may survive login.

Authentication state should be newly established.

Temporary security-sensitive state should be reviewed.

Do not blindly copy every anonymous-session field into an authenticated session.
