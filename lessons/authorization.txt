Authorization is the process of determining whether an authenticated or otherwise identified principal is permitted to perform a requested action on a resource.

Authorization answers:

What is this principal allowed to do?

Authorization does not establish identity.

Authentication establishes identity.

Authorization evaluates permissions.

Keep them separate.

A user can authenticate successfully and still be unauthorized.

An unauthenticated requester can sometimes be authorized to access a public resource.

Public access is an authorization decision.

Do not require authentication merely to claim that authorization exists.

Authorization requires a decision context.

The context commonly includes:

Principal.

Action.

Resource.

Applicable policy.

Relevant state.

The authorization decision determines whether the requested operation is permitted.

A useful authorization question is:

May principal P perform action A on resource R under policy C?

Every part matters.

Changing the principal can change the result.

Changing the action can change the result.

Changing the resource can change the result.

Changing applicable policy can change the result.

Changing relevant state can change the result.

Do not reduce authorization to a single boolean stored on the user account unless the system is genuinely that simple.

A permission represents authority to perform a defined operation.

Examples include:

Read a document.

Create a record.

Modify a record.

Delete a record.

Publish content.

Manage users.

Change configuration.

Execute an administrative operation.

Permissions should describe actual authority.

Do not use vague permission names when precise operations matter.

A role is a collection or classification of authority according to a system's access-control model.

Examples can include:

User.

Editor.

Administrator.

Operator.

Auditor.

Roles are application-defined.

The name of a role does not inherently define its permissions.

"Administrator" means only what the system's authorization policy says it means.

Do not infer permissions from a role's English name.

Role-Based Access Control is commonly abbreviated RBAC.

RBAC assigns permissions to roles.

Principals are assigned roles.

Authorization can then determine whether one of the principal's roles contains the required permission.

A simplified relationship is:

Principal -> Role -> Permission.

Real systems can include additional constraints.

Do not confuse RBAC with authentication.

RBAC assumes the principal has already been established or otherwise identified.

A role should not be supplied by an untrusted client as authoritative input.

The server determines the principal's roles from trusted authorization state.

Never authorize because a form field says:

role=admin

Never authorize because a URL parameter says:

admin=true

Never authorize because JavaScript hides a button from ordinary users.

Client-side state is not authorization authority.

The server must make the authoritative authorization decision.

Hiding a user-interface element can improve usability.

It does not prevent direct requests.

A user can construct HTTP requests manually.

A user can modify HTML.

A user can modify JavaScript.

A user can call an API directly.

Authorization must be enforced where the protected operation occurs.

Do not rely on the interface to enforce permissions.

Every protected server-side action should enforce the applicable authorization policy.

A page can be protected.

An API endpoint can be protected.

A command can be protected.

A database operation can be protected.

A file operation can be protected.

A message handler can be protected.

A background job can be protected.

Protection belongs at the authority boundary.

Do not assume requests only arrive through the expected user interface.

Authorization should normally occur after authentication when the resource requires an authenticated identity.

A common request sequence is:

Receive request.

Validate request structure sufficiently to identify the intended operation.

Authenticate the requester.

Establish the principal.

Determine the target resource.

Evaluate authorization.

If authorized, perform the operation.

If unauthorized, reject the operation.

Do not perform the protected state change before authorization completes.

Authorization after execution is auditing, not prevention.

A permission check should occur before the protected effect.

Do not write to the database and then ask whether the user was allowed to do it.

Do not delete the file and then evaluate the role.

Do not transmit protected information before checking read authority.

Authorization protects both state changes and information disclosure.

Read access is authority.

Write access is authority.

Execute access is authority.

Administrative access is authority.

Do not focus only on destructive operations.

Unauthorized reading can be a serious security failure.

Least privilege means a principal receives only the authority required for its legitimate function.

Do not grant broad administrative authority merely because it is easier to implement.

Narrow authority reduces the impact of mistakes and compromise.

A service that only reads records should not receive write permission.

A user who only edits their own profile should not receive global user-management authority.

A monitoring process should not receive configuration-changing authority unless required.

Authority should match purpose.

Default deny means access is denied unless policy explicitly permits it.

This is a strong baseline for protected systems.

Unknown permission should not become permission granted.

Missing role should not become administrator.

Missing policy should not become allow.

Ambiguous authorization state should not silently grant access.

When authority cannot be established, deny the protected operation.

Fail closed.

Do not confuse fail closed with crashing.

The application can return a controlled denial.

The application should remain stable.

The protected operation simply does not occur.

Authorization failure is a valid application state.

Handle it deliberately.

An allowlist defines what is permitted.

A denylist defines what is prohibited.

Authorization systems commonly benefit from explicit allowed operations.

A denylist alone can fail when new operations are introduced and are not added to the list.

Default-deny systems reduce that risk.

Do not assume an operation is safe merely because it is not explicitly forbidden.

Authorization policy should define the allowed authority.

Access Control Lists are commonly abbreviated ACLs.

An ACL associates resources or objects with access rules.

An ACL can specify which principals or groups may perform which operations.

For example:

User A can read File X.

Group B can read and modify File X.

User C has no access to File X.

ACLs are resource-oriented access-control structures.

Do not confuse ACLs with filesystem permissions specifically.

Filesystems can use ACLs.

Applications can also implement ACLs.

Discretionary Access Control is commonly abbreviated DAC.

DAC commonly allows an object's owner or another authorized principal to control access according to system rules.

Mandatory Access Control is commonly abbreviated MAC.

MAC enforces access according to centrally defined security labels or policy.

Do not confuse Mandatory Access Control with a network interface MAC address.

They share an abbreviation.

They are unrelated concepts.

Attribute-Based Access Control is commonly abbreviated ABAC.

ABAC evaluates attributes associated with subjects, resources, actions, and environment.

Example attributes can include:

Department.

Resource classification.

Employment status.

Device state.

Time.

Operation type.

ABAC can express policies more flexibly than simple roles.

Flexibility also increases policy complexity.

Do not add ABAC when a small role or ownership check solves the requirement.

Authorization architecture should remain as simple as the actual requirements allow.

Policy complexity creates failure opportunities.

Ownership-based authorization allows operations according to a defined ownership relationship.

For example:

A user may modify their own profile.

A user may read their own private document.

A user may delete a resource they created if policy permits it.

Ownership must be established from trusted server-side state.

Do not accept:

owner_id=<current user>

from the client as proof of ownership.

The server should load the resource.

The server should determine its recorded owner.

The server should compare that ownership with the authenticated principal according to policy.

Client claims do not establish ownership.

An object identifier identifies a resource.

It does not authorize access to that resource.

Knowing another user's resource ID does not grant permission to read it.

This distinction is critical.

Authorization must be evaluated after identifying the requested object.

Insecure Direct Object Reference is commonly abbreviated IDOR.

IDOR vulnerabilities occur when an application exposes object identifiers and fails to enforce appropriate authorization on access to those objects.

For example:

/documents/100

/documents/101

If User A is authorized for document 100 but can change the URL to 101 and receive User B's document without an authorization check, access control is broken.

The problem is not that identifiers are sequential.

Random identifiers can make discovery harder.

They do not replace authorization.

A UUID does not grant security merely because it is difficult to guess.

If an unauthorized user obtains the UUID, the server must still reject access.

Do not use unguessability as the only access-control mechanism for protected resources.

Capability-based systems intentionally use possession of an unforgeable capability as authority.

That is a specific authorization model.

Do not accidentally create a capability system merely by assuming nobody will discover a URL.

If possession is intended to grant authority, define the credential as a capability and protect it accordingly.

If possession is not intended to grant authority, enforce ordinary authorization.

Object-level authorization checks the requester's authority over the specific target object.

Function-level authorization checks whether the principal may perform a type of operation.

Both can be required.

A user can have permission to edit documents generally while lacking permission to edit a particular document.

Do not stop at function-level authorization when object ownership or scope matters.

For example:

Permission: edit_document.

Resource: document 123.

Policy can require both:

Principal has edit_document permission.

Principal is authorized for document 123.

One does not imply the other.

Administrative permission can intentionally override ordinary ownership restrictions.

If so, encode that rule explicitly.

Do not scatter undocumented administrator bypasses throughout the code.

Centralize authorization policy where practical.

Explicit policy is easier to review.

An authorization rule should be understandable.

For example:

Allow update when the principal owns the record.

Allow update when the principal has records.admin permission.

Otherwise deny.

This is clearer than:

if ($user)

where authentication is accidentally treated as universal authorization.

Authenticated does not mean authorized.

Roles can be hierarchical.

An administrator role can include permissions from an editor role.

An editor can include permissions from a viewer role.

Role inheritance should be explicit.

Do not infer hierarchy from role names.

A role called "senior_editor" does not automatically inherit "editor" unless policy says so.

Role hierarchies can simplify policy.

They can also create hidden privilege expansion.

Review inherited permissions.

A role change can affect many permissions at once.

Treat role assignment as a security-sensitive operation.

Only authorized principals should assign privileged roles.

Do not let users modify their own role fields unless explicitly permitted.

Mass assignment can create authorization vulnerabilities.

Suppose an account update accepts:

name

email

role

If ordinary users should only modify name and email, accepting role from the request can allow privilege escalation.

Use explicit writable-field allowlists.

Do not bind every request field directly into privileged models.

Privilege escalation occurs when a principal gains authority beyond what policy permits.

Vertical privilege escalation moves toward more privileged authority.

For example:

Ordinary user becomes administrator.

Horizontal privilege escalation accesses another principal's resources at the same nominal privilege level.

For example:

User A accesses User B's private record.

Both are authorization failures.

Do not focus only on administrator escalation.

Horizontal access-control failures are common and serious.

Authorization boundaries should be tested for both.

For every protected operation, test:

Authorized principal succeeds.

Unauthenticated requester behaves according to policy.

Authenticated but unauthorized principal is denied.

Wrong owner is denied.

Wrong role is denied.

Revoked authority is denied.

Malformed or manipulated identifiers do not bypass checks.

Negative authorization testing is essential.

A test suite that verifies only successful authorized operations does not establish access-control enforcement.

Try to violate the policy.

Authorization tests should operate at the actual enforcement boundary.

If the HTTP endpoint performs the check, test the endpoint.

If the service layer performs the check, test the service layer.

If both are expected to enforce independent boundaries, test both.

Do not test only whether a button is hidden.

UI tests are not sufficient evidence of server authorization.

Put checks where sufficient evidence exists.

Evaluate current policy where required.
