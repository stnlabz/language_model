Choosing a status code should follow the actual condition.
If no HTTP failure occurred, an internal knowledge response should not fabricate one.
If an answer cannot be established from available evidence, the response should say that the evidence is insufficient.
If no matching knowledge exists, the response should report the knowledge miss according to the application's contract.
If an internal service required for the operation is genuinely unavailable, service-unavailable reporting is appropriate.
If an internal service is available but returns no matching record, service-unavailable reporting is inappropriate.
If a module is active and successfully executes but finds no answer, the module did not become unavailable merely because its result was empty.
If a module crashes or cannot execute a required operation, that is an execution failure.
If module discovery fails, that is a discovery failure.
If module qualification fails, that is a qualification failure.
If routing cannot identify a handler, that is a routing failure.
If retrieval returns no relevant evidence, that is a retrieval miss.
If evidence exists but does not support a conclusion, that is insufficient evidence.
If evidence supports multiple incompatible conclusions, that is contradictory evidence.
These failure and knowledge states should remain distinct.
Correct HTTP handling preserves those distinctions at the transport boundary.
