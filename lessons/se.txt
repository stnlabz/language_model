Post-incident review examines what happened and how the system can improve.

The purpose is engineering improvement.

Useful questions include what failed.

Useful questions include why detection occurred when it did.

Useful questions include why controls did or did not work.

Useful questions include how recovery behaved.

Useful questions include what evidence was missing.

Useful questions include what change would prevent recurrence.

Do not assume every incident requires architectural redesign.

Sometimes the correct repair is small.

Sometimes a small symptom reveals a large architectural defect.

Evidence determines scope.

A specification defines required behavior.

An implementation realizes the specification.

A test evaluates implementation behavior against defined expectations.

Documentation explains the system.

Operations run the system.

Monitoring observes the system.

Maintenance changes the system.

These activities form a lifecycle.

Software engineering manages that lifecycle deliberately.

Good engineering preserves working behavior while changing required behavior.

Good engineering limits unnecessary scope.

Good engineering produces evidence.

Good engineering recognizes uncertainty.

Good engineering uses clear interfaces.

Good engineering handles failure.

Good engineering validates assumptions.

Good engineering tests claims.

Good engineering respects authority boundaries.

Good engineering keeps systems understandable.

Do not confuse more code with more capability.

Do not confuse abstraction with architecture.

Do not confuse architecture with complexity.

Do not confuse compilation with correctness.

Do not confuse execution with success.

Do not confuse one passing test with validation.

Do not confuse a symptom with root cause.

Do not confuse a workaround with a repair.

Do not confuse a warning with proof of a defect.

Do not confuse absence of evidence with evidence of absence.

Do not confuse newer with correct.

Do not confuse automated with authoritative.

Do not confuse technically possible with authorized.

Do not confuse configuration with state.

Do not confuse current state with history.

Do not confuse retry with recovery.

Do not confuse availability with correctness.

Do not confuse performance with scalability.

Do not confuse source compatibility with binary compatibility.

Do not confuse an API with its implementation.

Do not confuse a module with the core that hosts it.

Do not confuse a successful build with a successful release.

When changing software, establish what is wrong.

Establish what correct behavior should be.

Establish which component owns that behavior.

Establish what evidence demonstrates the defect.

Make the smallest appropriate change.

Build it.

Test it.

Test relevant boundaries.

Observe the result.

Preserve evidence.

Report what actually happened.

If the result is unknown, say it is unknown.

If the result failed, say it failed.

If the result passed, state what specifically passed.

Software engineering is controlled change applied to software systems.

The objective is not merely to make code work once.

The objective is to make required behavior understandable, testable, maintainable, reproducible, and dependable.
