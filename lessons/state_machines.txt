State machines describe systems whose behavior depends on their current state and on defined transitions between states.

A state represents a meaningful condition of a system.

A transition represents a permitted movement from one state to another.

An event is something that can cause a transition to be considered.

A guard is a condition that must be satisfied before a transition can occur.

An action is work performed as part of a transition.

Keep these concepts separate.

A basic state machine can be represented as:

Current State + Event + Conditions -> Next State

For example:

DISCONNECTED + CONNECT -> CONNECTING

CONNECTING + CONNECTION_SUCCESS -> CONNECTED

CONNECTING + CONNECTION_FAILURE -> DISCONNECTED

CONNECTED + DISCONNECT -> DISCONNECTED

The current state matters.

The same event can produce different behavior in different states.

For example:

CONNECT while DISCONNECTED can begin a connection.

CONNECT while CONNECTED can be rejected or ignored according to policy.

Do not assume an event always means the same transition.

State defines context.

A finite-state machine has a finite set of defined states.

For example:

STOPPED

STARTING

RUNNING

STOPPING

FAILED

The system should know which states exist.

Do not create states implicitly through combinations of unrelated flags unless that complexity is intentional.

Multiple Boolean flags can accidentally represent impossible conditions.

For example:

is_running = true

is_stopped = true

is_starting = true

What state is the system actually in?

A single explicit state can make the invariant clearer.

state = RUNNING

Use explicit states when behavior is fundamentally state-dependent.

Not every Boolean requires a state machine.

A feature that is simply enabled or disabled can remain a Boolean.

Do not introduce state-machine complexity where two independent values are sufficient.

Use a state machine when transitions and sequencing matter.

States should represent meaningful system conditions.

Avoid vague states such as:

BUSY

OTHER

UNKNOWN_STATE_2

unless their semantics are explicitly defined.

A state name should communicate what condition exists.

For example:

UNINITIALIZED

READY

FAILED

State names are part of the model.

Choose them deliberately.

A state machine should define its initial state.

For example:

INITIAL STATE: DISCONNECTED

Do not leave initialization dependent on uninitialized memory, arbitrary database contents, or whichever event arrives first.

Initial state must be deterministic.

Initialization can itself be a state.

For example:

UNINITIALIZED

READY

FAILED

This can make startup behavior explicit.

A terminal state is a state from which no ordinary transition continues.

Examples can include:

COMPLETED

CANCELLED

TERMINATED

Terminal does not necessarily mean the process exits.

It means the modeled lifecycle is finished according to that state machine.

Define terminal behavior.

Do not accidentally permit transitions out of a terminal state unless policy explicitly allows them.

Anything not defined is not automatically permitted.

Default behavior for undefined transitions should be explicit.

Common choices include:

Ignore.

Log and ignore.

Return an error.

Escalate according to policy.

Do not invent a transition because an unexpected event arrived.

An event does not authorize an arbitrary transition.

Only a defined transition does.

This is fundamental.

Suppose the machine defines:

STOPPED + START -> STARTING

RUNNING + STOP -> STOPPING

Receiving:

STOPPED + STOP

does not mean the machine should guess that STOPPED is already the desired state and report success unless that behavior is explicitly defined.

It can reject.

It can treat the operation as idempotent.

Either design can be correct.

Define it.

Do not guess.

State transitions should be deterministic.

Given the same:

Current state.

Event.

Guard conditions.

Relevant authoritative data.

The same transition decision should result.

Do not use probability to decide deterministic lifecycle transitions.

A system is not "probably RUNNING."

It is in the state established by its state model.

If state cannot be determined, represent that condition explicitly or fail safely according to policy.

Do not invent certainty.

Transition validity should be checked before changing state.

Conceptually:

if transition_is_valid(current_state, event):
    next_state = defined_transition(current_state, event)
else:
    reject_event()

Do not change state first and validate afterward.

The current state is part of the evidence for whether the transition is permitted.
