Source files are inputs.

Headers are inputs.

Compiler flags are inputs.

Preprocessor definitions are inputs.

Toolchain version is input.

Libraries are inputs.

Linker flags are inputs.

Target architecture is input.

Environment can be input.

Generated code can be input.

A build artifact is the result of all relevant build inputs.

Source code alone does not fully describe a build when other inputs affect output.

Build configuration should therefore be controlled.

Do not modify compiler flags casually when they affect semantics.

Changing optimization can expose defects.

Changing structure packing can break ABI.

Changing runtime-library selection can change dependencies.

Changing exception or RTTI settings can change C++ interfaces.

Changing character-set settings can change Windows program behavior.

Changing architecture changes binary compatibility.

A compiler switch is part of engineering state.

Warnings-as-errors policies can improve discipline.

Warnings-as-errors can also cause builds to fail when a new compiler introduces new warnings.

Toolchain upgrades should be controlled.

Do not freeze obsolete toolchains merely to avoid fixing legitimate diagnostics.

Do not upgrade production toolchains casually without validation.

Toolchains are dependencies.

A compiler can contain defects.

A linker can contain defects.

A standard library can contain defects.

A toolchain defect is possible.

It should not be the first explanation for ordinary application failure without evidence.

Check source correctness.

Check undefined behavior.

Check configuration.

Check ABI.

Check dependencies.

Check runtime environment.

Then investigate toolchain defects when evidence points there.

Disassembly translates machine code into assembly-like representation.

Disassembly can show what instructions were actually generated.

Disassembly is useful when source behavior and runtime behavior appear inconsistent.

Disassembly can verify optimization.

Disassembly can verify function presence.

Disassembly can verify call targets.

Disassembly can help analyze crashes.

Do not begin with disassembly when source-level evidence already identifies the defect.

Use the simplest diagnostic level that resolves the problem.

A debugger can operate on compiled binaries.

Debug symbols improve source-level debugging.

Breakpoints pause execution at defined locations.

Watchpoints detect selected memory accesses or changes where supported.

Stack traces show active call frames.

A stack trace is evidence about one execution state.

A stack trace does not automatically identify root cause.

The crash site can be downstream from earlier corruption.

Memory corruption can occur long before detection.

Inspect surrounding evidence.

Core dumps preserve process state after selected crashes on Unix-like systems.

Windows crash dumps preserve process state for postmortem analysis.

Dump analysis should use matching binaries and symbols.

Mismatched symbols can mislead diagnosis.

Artifact retention supports postmortem debugging.

A release process can retain exact binaries.

A release process can retain matching symbols.

A release process can retain build logs.

A release process can retain hashes.

A release process can retain source revision identifiers.

These records improve reproducibility.

Compilation should be deterministic where project requirements demand it.

Timestamps can affect output.

Randomized identifiers can affect output.

Archive member ordering can affect output.

Toolchain versions can affect output.

Reproducible-build engineering controls these inputs.

Reproducibility provides evidence that source and build instructions correspond to distributed artifacts.

Reproducibility does not establish that the source is correct.

Build provenance and behavioral correctness are different.

The compiler is not an authority over project requirements.

The compiler enforces language and toolchain rules.

The linker enforces binary composition requirements.

The loader enforces executable-loading requirements.

The application enforces its own architecture and policy.

Passing one layer does not establish success at another layer.

A valid source file can fail to link.

A linked executable can fail to load.

A loaded executable can fail initialization.

An initialized program can fail its operation.

A completed operation can produce an incorrect result.

Each stage requires its own evidence.

When a build fails, identify the stage.

If preprocessing fails, inspect preprocessing input and directives.

If compilation fails, inspect source and compiler diagnostics.

If assembly fails, inspect generated or supplied assembly and target configuration.

If linking fails, inspect symbols, objects, libraries, architecture, and linker arguments.

If loading fails, inspect runtime dependencies, binary architecture, and loader behavior.

If initialization fails, inspect application and module initialization.

Do not repair a later stage when evidence shows an earlier stage failed.

When a binary behaves incorrectly, confirm the exact artifact.

Confirm the source revision.

Confirm the build configuration.

Confirm the target.

Confirm the dependencies.

Confirm the runtime environment.

Then investigate program behavior.

Build evidence matters.

Artifact identity matters.

Language semantics matter.

ABI boundaries matter.

Platform boundaries matter.

The toolchain transforms source into executable artifacts.

The engineering task is to make that transformation controlled, reproducible, diagnosable, and compatible with the intended target.

A compiler translates code.

A linker connects compiled components.

A loader places executable components into a running process.

None of them determine whether the software fulfills its mission.

That remains a property of the complete engineered system.
