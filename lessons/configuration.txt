Configuration is the process of supplying a system with values that select or adjust behavior without requiring the program itself to be rewritten.

Configuration can determine:

Network addresses.

Ports.

Filesystem locations.

Logging levels.

Feature enablement.

Resource limits.

Timeouts.

Retry limits.

Module selection.

Runtime modes.

Service endpoints.

Database connections.

Protocol options.

Operational parameters.

Configuration should select among behavior the software is designed and authorized to perform.

Configuration should not secretly redefine the architecture of the system.

Code defines capability.

Policy defines permitted behavior where policy applies.

Configuration selects permitted operating parameters.

Keep these concepts separate.

A configuration value is input.

Treat configuration as input.

Do not assume configuration is valid merely because it came from a local file.

Configuration can be:

Malformed.

Incomplete.

Outdated.

Mistyped.

Corrupted.

Generated incorrectly.

Modified manually.

Copied from another environment.

Incompatible with the running software.

Validate configuration before using it.

A useful configuration lifecycle is:

Discover configuration source.

Read configuration.

Parse configuration.

Validate structure.

Validate values.

Resolve precedence.

Apply defaults where defined.

Construct the effective configuration.

Validate cross-field relationships.

Freeze or publish the effective configuration.

Use it.

Do not begin operating on partially validated configuration.

Configuration formats can include:

Plain text.

TSV.

CSV.

INI.

JSON.

YAML.

TOML.

XML.

Environment variables.

Command-line arguments.

Database records.

Operating-system configuration stores.

Remote configuration services.

Compiled defaults.

The format is not the configuration architecture.

Choose a format appropriate to the system.

Do not adopt a complex format merely because it is popular.

Small systems often benefit from simple configuration.

A configuration schema defines what configuration is accepted.

The schema can specify:

Known keys.

Required keys.

Optional keys.

Types.

Ranges.

Allowed values.

Defaults.

Relationships.

Deprecations.

Version.

For example:

host = string

port = integer from 1 through 65535

timeout_seconds = integer from 1 through 300

log_level = one of debug, info, warning, error

enabled = boolean

Do not accept arbitrary values and hope downstream code handles them.

Configuration validation should fail clearly.

For example:

Invalid:

port=banana

Do not silently convert it to:

port=0

Reject it.

Invalid:

port=70000

Do not clamp it to:

65535

Reject it.

Invalid:

log_level=verboseish

Do not guess:

debug

Reject it.

Configuration should be deterministic.

The same configuration sources under the same precedence rules should produce the same effective configuration.

Do not make configuration resolution depend on arbitrary iteration order.

Do not randomly choose between duplicate settings.

Define precedence.

A common precedence model can be:

Compiled defaults.

System configuration file.

Application configuration file.

Environment variables.

Command-line arguments.

The exact order is application-specific.

There is no universal precedence hierarchy.

Define one.

Document it.

Implement it consistently.

Do not let different modules invent different precedence rules.

For example, if command-line options override environment variables, that rule should apply consistently unless an option explicitly defines otherwise.

Precedence answers:

When multiple sources provide the same setting, which one wins?

It does not answer:

Is the winning value valid?

Validate the resulting value.

A higher-precedence source should not be allowed to bypass validation.

For example:

File:

port=8080

Environment:

PORT=banana

If environment has higher precedence, the effective input is invalid.

Do not fall back silently to 8080 unless fallback-on-invalid is explicitly defined.

Invalid override is not the same as absent override.

This distinction matters.

Absent means:

No value was supplied by this source.

Invalid means:

A value was supplied but violates the contract.

Do not treat malformed configuration as missing configuration.

Defaults apply to absent optional configuration according to defined rules.

Defaults should not normally conceal malformed supplied values.

For example:

Default port = 8080.

PORT absent:

Use 8080.

PORT=abc:

Reject configuration.

Do not use 8080 merely because parsing abc failed.

Otherwise configuration mistakes become invisible.

Defaults should be explicit.

Do not scatter hidden defaults throughout the program.

For example:

network.c assumes timeout=10.

worker.c assumes timeout=30.

api.c assumes timeout=60.

This creates inconsistent behavior.

Define the authoritative default once where practical.

Defaults are part of system behavior.

Document important defaults.

A default should be safe and meaningful.

Do not choose insecure defaults merely because they make setup easier.

For example:

authentication_required = false

can be a dangerous default if authentication is required by the product's security model.

Security-sensitive defaults should follow policy.

Do not let missing configuration silently disable required protections.

Required configuration should be required.

If the system cannot operate correctly without a value, do not invent one unless a defined default exists.

For example:

Required cryptographic identity file missing.

Do not silently generate or select an unrelated identity unless the system explicitly defines that behavior.

Fail clearly or enter the defined initialization workflow.

Do not guess.

Configuration is an interface.

Treat key names as interface design.

Grouping can improve clarity.

Do not create unnecessary hierarchy for a tiny configuration.

Keep it proportional.

Configuration types should remain explicit.

A boolean is not an arbitrary string.

Define accepted forms.

For example:

true

false

Do not accept:

yes

y

1

on

enabled

unless the configuration specification explicitly allows them.

Permissive parsing can create ambiguity.

If multiple forms are accepted, define them exactly.

Integer configuration should be parsed strictly.

Check:

Complete parse.

Range.

Overflow.

Sign.

Do not use permissive conversion that accepts prefixes and ignores trailing garbage.

For example:

18473abc

should not become:

18473

if the configuration requires an integer.

Floating-point configuration requires defined semantics.

If only finite values are permitted, reject:

NaN

Infinity

-Infinity

Define range and precision requirements.

Do not use floating point for values requiring exact integer or decimal semantics merely because parsing is convenient.

Durations should have clear units.

Bad:

timeout=30

Thirty what?

Seconds?

Milliseconds?

Minutes?

Prefer either a documented universal unit:

timeout_seconds=30

or a defined duration grammar:

timeout=30s

Do not make units depend on which module reads the value.

Storage sizes should also have defined units.

For example:

cache_bytes=1048576

or:

cache_size=1MiB

if the parser explicitly supports that grammar.

Do not interpret:

1M

differently on different platforms or modules.

Configuration paths should have defined semantics.

Questions include:

Absolute or relative?

If relative, relative to what?

Working directory?

Executable directory?

Configuration file directory?

Data directory?

Define it.

Do not let path interpretation depend accidentally on where the process was launched.

A service started by systemd can have a different working directory than the same binary launched manually.

Relative-path ambiguity creates deployment defects.

Canonicalize paths where appropriate.

Do not canonicalize away meaningful semantics blindly.

Validate path existence only when existence is required at configuration time.

For example:

Input file must exist.

Output directory might be created later.

Know the requirement.

Do not require every configured path to exist merely because path validation exists.

Permissions matter.

A path can exist while the process cannot read or write it.

Configuration validation can check required access where practical.

Do not claim a path is usable merely because stat() succeeded.

The actual operation can still fail.

Runtime error handling remains required.

Configuration validation reduces predictable failures.

It cannot prove future operations will succeed.

Hostnames and addresses should use appropriate parsers.

Do not parse network endpoints through casual string splitting when IPv6 or other valid formats can contain colons.

Define endpoint representation.

For example:

host and port as separate fields.

This can be clearer than one overloaded string.

If a URL is expected, parse it as a URL.

If a hostname is expected, do not accept an arbitrary URL unless explicitly supported.

Keep types distinct.

Ports must be validated according to the application's permitted range.

The general transport range can be 1 through 65535.

An application can impose a narrower allowed range.

Do not assume any numerically valid port is permitted by application policy.

For example:

Another example:

can require:

server_port

Another:

Validate combinations.

Individually valid values can form an invalid configuration.

Configuration modes should have defined behavior.

For example:

development

test

production

Do not let a mode become a vague switch that changes dozens of undocumented behaviors.

If a mode affects behavior, document what it selects.

Security behavior should not be hidden behind surprising mode semantics.

For example:

production=true

should not be the only thing preventing debug authentication bypass unless that architecture is explicitly designed and controlled.

Prefer explicit security settings where clarity matters.

Feature flags are configuration.

A feature flag selects whether an existing feature is active.

It should not introduce code paths that have never been validated.

Feature flags can be:

Boolean.

Enumerated.

Percentage-based.

Identity-based.

Time-based.

Simple systems should prefer simple flags.

Do not build an experimentation platform when a boolean is sufficient.

A feature disabled by configuration still exists in the code.

Do not confuse disabled with absent.

Security analysis should consider dormant code if it can be re-enabled.

Configuration can select modules.

For example:

modules=network,storage,monitoring

Validate module names.

Reject unknown modules unless forward-compatible behavior explicitly allows them.

Do not dynamically load arbitrary paths merely because a configuration key says:

module=/tmp/whatever

unless arbitrary module loading is intentionally authorized.

Module selection and module trust are separate.

Configuration can select among approved components.

It does not automatically authorize arbitrary executable code.

Plugin paths are security boundaries.

Treat them accordingly.

A configuration file can be human-editable.

Human-editable configuration should produce useful errors.

For example:

This is more useful than:

Include enough context to correct the error.

Do not expose secrets in error messages.

For example:

Invalid API token format.

Do not print the entire token.

For example:

or:

source = command line

Knowing provenance helps debugging.

Do not make operators guess which layer supplied the effective value.

Deployment verification.

First value wins.

Collect into list.

Choose intentionally.

Do not claim configuration files are universally insecure.

Do not make a configuration file world-writable.

Configuration integrity matters.

Do not declare configuration invalid because a remote service is temporarily down unless reachability is explicitly part of configuration validation.

This distinction improves diagnosis.

A useful startup sequence can be:

Load configuration.

Validate configuration.

Initialize local resources.

Validate required identities.

Connect dependencies.

Qualify dependencies.

Enter operational state.

If dependency connection fails, report dependency failure.

Do not report:

invalid configuration

unless configuration itself is invalid.

Error categories should preserve cause.

Configuration parsing errors are different from:

Permission errors.

Missing files.

Network failures.

Authentication failures.

Dependency failures.

State corruption.

Keep categories distinct.

For example:

CONFIG_FILE_NOT_FOUND

CONFIG_PARSE_ERROR

CONFIG_UNKNOWN_KEY

CONFIG_INVALID_VALUE

CONFIG_CONFLICT

CONFIG_PERMISSION_DENIED

These can aid diagnostics.

Do not create hundreds of categories without operational value.

Use enough structure to identify the failure class.

A configuration file missing can have different semantics depending on whether the file is required.

Optional file absent:

Continue.

Required file absent:

Fail.

Do not treat all missing files identically.

An unreadable file is not the same as an absent file.

For example:

File exists but permission denied.

Do not silently treat it as absent and use defaults.

That can bypass intended configuration.

Report the permission failure.

Likewise, a malformed file is not absent.

Reject it.

This principle is important:

Missing optional configuration can fall back.

Present but invalid configuration should normally fail.

Do not reward corruption by silently ignoring it.

Configuration should support reproducibility.

If two deployments are intended to behave identically, their effective configuration should be comparable.

A normalized effective configuration can help.

For example:

network.host=127.0.0.1
network.port=8080
network.timeout_seconds=30
logging.level=info

Stable ordering makes diffs useful.

Do not include secrets in ordinary configuration comparisons.

Hashing configuration can provide an identifier for a specific effective configuration.

For example:

config_hash = SHA-256(normalized_nonsecret_or_complete_internal_representation)

The exact representation must be defined if the hash has operational meaning.

Do not hash arbitrary serializer output and assume stability across versions.

Canonicalization matters.

A configuration hash can help answer:

Are these two processes running equivalent configuration?

It does not prove the configuration is correct.

It does not prove authorization.

It is an identity for bytes or canonical data.

Do not overstate it.

Configuration revisions can be useful.

For example:

revision=17

The process can report:

loaded revision 17

This improves auditability.

Do not use revision numbers as substitutes for content validation.

A revision can contain malformed data.

Validate it.

Remote configuration introduces additional concerns.

A remote configuration service can fail.

Responses can be stale.

Authentication can fail.

Network partitions can occur.

Updates can arrive out of order.

Do not make a small local application depend on remote configuration without a reason.

If remote configuration is used, define:

Authentication.

Integrity.

Caching.

Startup behavior when unavailable.

Update ordering.

Rollback.

Versioning.

Staleness limits.

Authority.

Do not blindly accept whatever a remote endpoint returns.

Validate remote configuration exactly like local configuration.

Remote source does not eliminate schema validation.

Configuration updates can carry versions.

For example:

revision 42

revision 43

If revision 42 arrives after 43, reject it as stale where monotonic ordering is required.

Do not roll configuration backward accidentally.

Intentional rollback should be explicit.

A rollback is not the same as receiving stale data.

Dynamic configuration can use a state machine.

For example:

ACTIVE

RELOAD_PENDING

VALIDATING

APPLYING

ACTIVE

RELOAD_FAILED

This can be useful for complex systems.

Do not introduce a configuration state machine when an atomic reload function is sufficient.

Keep systems small.

Configuration can interact with modules.

A module should receive the configuration it owns.

Do not give every module unrestricted access to every configuration value unless needed.

Scoped configuration reduces coupling.

For example:

network module receives network configuration.

storage module receives storage configuration.

logging module receives logging configuration.

This makes dependencies explicit.

A module should not secretly read random global environment variables if configuration is supposed to be centralized.

Centralize acquisition.

Distribute validated typed values.

This produces one effective configuration.

It also makes testing easier.

A module test can supply:

NetworkConfig {
    host,
    port,
    timeout
}

without constructing the entire application environment.

Typed configuration is preferable to repeatedly querying strings.

For example:

Bad:

get_config("network.port")

every time a connection opens.

Better:

network_config.port

where port is already a validated integer.

Do parsing at the boundary.

Use typed values internally.

Do not repeatedly reinterpret raw configuration.

Configuration should not determine implementation details that should remain internal.

For example:

algorithm_internal_buffer_index=7

might expose unnecessary internals.

Expose configuration only where operators have a legitimate reason to select behavior.

Every configuration option becomes:

Documentation burden.

Testing burden.

Compatibility burden.

Support burden.

Security surface.

Do not make everything configurable.

Hard-coded is not automatically bad.

A protocol constant can belong in code.

A safety invariant can belong in code.

A fixed file signature can belong in code.

A consensus rule can belong in protocol logic.

Configuration is appropriate when legitimate deployments need different values.

Ask:

Who needs to change this?

Why?

Under what authority?

How often?

What values are valid?

What happens if it is wrong?

If there is no good answer, it may not need to be configurable.

Too much configuration creates accidental complexity.

A system with 500 knobs can be harder to operate than one with 20 well-chosen settings.

Prefer meaningful configuration.

Small.

Deterministic.

Easy to understand.

Configuration names should not require reading source code to understand basic behavior.

Documentation should explain:

Purpose.

Type.

Default.

Allowed range.

Whether required.

Source precedence.

Reload behavior.

Security implications where relevant.

Example.

For example:

Type: integer

Range: 1..65535

Default: 18473

Reload: restart required

Purpose: local RPC listener port

This is useful.

Configuration documentation should match implementation.

Test examples where practical.

Stale configuration documentation causes operational errors.

When removing a configuration key:

Deprecate if compatibility requires it.

Warn.

Provide replacement.

Remove according to version policy.

Do not silently reinterpret the old key as something unrelated.

Meaning should remain stable.

When renaming:

old_name -> new_name

define transition behavior.

Possible approach:

Accept old_name with warning.

Reject both old_name and new_name together if ambiguous.

Later remove old_name.

Do not let both independently control the same behavior without defined precedence.

Configuration aliases can create ambiguity.

Use them temporarily and deliberately.

Configuration values should not be copied into unrelated mutable globals.

Build the effective configuration object.

Pass required values to components.

This makes ownership visible.

Global configuration access can be convenient.

It can also hide dependencies.

Use it deliberately.

A function requiring a timeout should receive or access the appropriate validated timeout through a clear interface.

Do not have low-level functions secretly parse environment variables.

Parsing belongs at boundaries.

Configuration can influence logging.

For example:

log_level=info

Changing logging level should not change application correctness.

Debug logging should not be required for the program to function.

Do not put side effects inside logging expressions that disappear when logging is disabled.

Configuration can influence performance.

For example:

worker_count.

cache_size.

batch_size.

Validate resource bounds.

Do not allow:

worker_count=1000000

if that would exhaust the system.

Operational limits are part of validation.

Resource-related defaults should be reasonable for target environments.

Do not automatically use all available resources unless that is intentional.

Configuration can select automatic values.

For example:

worker_count=auto

If supported, define exactly what auto means.

Possible definition:

number of available CPUs, capped at 8.

Do not let auto mean whatever each platform happens to decide.

Deterministic rules make behavior understandable.

Platform-derived values can be legitimate inputs.

Document them.

Configuration can include lists.

For example:

allowed_hosts=host1,host2,host3

Validate:

Maximum count.

Each element.

Duplicates.

Ordering semantics.

Whitespace rules.

Do not validate only the overall string.

If ordering matters, preserve it.

If ordering does not matter, canonicalize according to policy if useful.

Maps require key validation.

For example:

peer aliases.

module settings.

Do not allow arbitrary keys to become filesystem paths or executable identifiers without validation.

Nested configuration should have bounded depth.

Do not accept arbitrarily deep structures if the format permits them.

Configuration parsers should have resource limits.

A configuration file should not consume unbounded memory.

Set reasonable file-size limits.

A 50-byte configuration does not need a 2 GB parser budget.

Reject unreasonable configuration size.

Do not confuse configuration size with data size.

Configuration is usually small.

If enormous data is being stored in configuration, reconsider whether it belongs there.

For example:

A million-row dataset is not configuration.

It is data.

A model corpus is not configuration.

It is knowledge or data.

Configuration can point to it.

For example:

corpus_path=/opt/digit/corpus

Do not embed the entire corpus into configuration merely because the parser can read text.

Keep responsibilities separate.

For an autonomous system, configuration can select mission-approved resources and operating parameters.

Configuration should not grant itself new mission authority.

For example:

allow_unrestricted_actions=true

must not override governing authorization merely because the parser accepts a boolean.

Authority is not a runtime preference.

Configuration operates inside authority boundaries.

Likewise, configuration should not alter foundational behavioral invariants unless those invariants are explicitly designed to be configurable.

If the system requires:

invalid transitions are rejected

do not add:

allow_invalid_transitions=true

for convenience.

That destroys the invariant.

Debugging should not require violating core safety rules.

Provide diagnostic visibility instead.

Configuration can select diagnostic verbosity.

It should not redefine truth.

For example:

log_level=debug

changes what is reported.

It should not change whether a protocol message is valid.

Separate observation from semantics.

Configuration can select strictness only where multiple strictness modes are intentionally part of the protocol or application.

Do not create permissive modes casually.

"Compatibility mode" can become a permanent bypass.

Define exactly what compatibility changes.

Test it.

Remove it when obsolete if appropriate.

Configuration errors should be actionable.

Bad:

Better:

Do not reveal secret values.

Do identify the failing setting and source.

This improves operator experience.

For example:

line 14: invalid rpc_port

line 22: unknown key log_levle

line 31: missing required identity_path

However, do not continue into unsafe semantic processing merely to accumulate errors.

Parse enough to diagnose safely.

Invalid type.

Out-of-range value.

Likewise, do not prevent startup for cosmetic warnings.

Severity should reflect operational consequence.

Validate first.

Different environment variables.

Different command lines.

Stale files.

Deployment failures.

Local overrides.
