Inter-process communication, or IPC, is the exchange of data, signals, or synchronization information between separate processes.

Processes normally have separate address spaces.

One process cannot ordinarily access another process's memory directly.

IPC provides controlled mechanisms for processes to communicate.

Common IPC mechanisms include:

Anonymous pipes.

Named pipes.

FIFOs.

Unix domain sockets.

TCP sockets.

UDP sockets.

Shared memory.

Message queues.

Signals.

Semaphores.

Memory-mapped files.

Platform-specific IPC facilities.

Different IPC mechanisms solve different problems.

Do not choose IPC merely because a mechanism is familiar.

Choose the smallest mechanism that satisfies the communication requirements.

Before selecting IPC, determine:

Which processes communicate?

Are they on the same machine?

Can they be on different machines?

Is communication one-way or bidirectional?

Is communication request-response or asynchronous?

How much data is exchanged?

Does message ordering matter?

Does message delivery need acknowledgement?

Can messages be duplicated?

Can messages be lost?

Does communication require authentication?

Does communication cross a privilege boundary?

What happens when one process exits?

What happens when communication fails?

What latency and throughput are required?

What platform support is required?

IPC is an interface.

Treat it with the same discipline as any other interface.

Define:

Message format.

Message boundaries.

Ordering.

Error behavior.

Connection lifecycle.

Size limits.

Timeouts.

Authentication where required.

Authorization where required.

Versioning where required.

Do not let two processes depend on undocumented assumptions.

A pipe is a byte stream.

An anonymous pipe is commonly created by one process and inherited by related processes.

Typical uses include:

Parent-to-child communication.

Child-to-parent communication.

Connecting command-line programs.

Redirecting standard input.

Redirecting standard output.

A pipe does not inherently contain application-level messages.

If a process writes:

HELLO

then:

WORLD

the reader should not assume two reads will return exactly those two writes.

Byte streams do not preserve application message boundaries.

Define framing if messages matter.

A simple line-oriented protocol can use:

MESSAGE\n

This works when:

Messages cannot contain unescaped newlines.

Maximum line length is bounded.

Encoding is defined.

More complex protocols can use length prefixes.

For example:

4-byte length

followed by:

payload bytes

The receiver reads the length.

Validates it.

Then reads exactly that many payload bytes.

Do not allocate memory from an untrusted length field before validating its range.

For example:

length = 4294967295

must not cause an enormous allocation merely because the field is syntactically valid.

Set protocol limits.

A reader must handle partial reads.

Requesting 100 bytes does not guarantee one read operation returns 100 bytes.

The operating system can return fewer bytes.

Continue reading until:

The required amount is received.

EOF occurs.

An error occurs.

A timeout or cancellation condition occurs.

Do not treat a short read as automatically meaning the complete message arrived.

Likewise, writes can be partial.

A request to write 100 bytes can write fewer than 100.

Handle the actual number of bytes written.

Do not assume one write operation transmits the entire buffer unless the API explicitly guarantees it for that operation and size.

Standard input and standard output can form an IPC interface.

A parent process can launch a child process and communicate through stdin and stdout.

This is often a useful design for small tools.

For example:

Parent sends requests through child stdin.

Child sends structured responses through stdout.

Child sends diagnostics through stderr.

Keep protocol output separate from diagnostic output.

Do not write arbitrary log messages into stdout if stdout is carrying machine-readable protocol data.

Use stderr or another logging channel.

Otherwise the parent cannot distinguish:

Protocol response.

Debug message.

Warning.

Status text.

This can corrupt the interface.

Exit status is also communication.

A child process can return an exit code.

For example:

0 = success

nonzero = failure

The exact meaning of nonzero values should be defined if callers depend on them.

Do not encode large amounts of information into exit codes.

They are small status channels.

Use stdout, stderr, files, sockets, or another mechanism for detailed results.

An exit code is not a substitute for structured error information when structured information is required.

EOF has meaning.

For a pipe or socket, EOF commonly means the other side closed its writing endpoint or connection.

Do not interpret EOF as an empty message.

Empty payload and closed stream are different conditions.

Handle them separately.

Named pipes and FIFOs allow independently started processes to communicate through a named operating-system object.

On Unix-like systems, a FIFO can appear in the filesystem.

One process writes.

Another reads.

FIFOs can be useful for simple local communication.

They also require lifecycle management.

Consider:

Who creates the FIFO?

Who owns it?

What permissions does it have?

What happens if it already exists?

What happens if no reader exists?

Who removes it?

Could an attacker create it first?

Do not blindly trust a filesystem object because it has the expected pathname.

Validate ownership and permissions where the IPC boundary is security-sensitive.

Named pipes on Windows provide a different platform mechanism with similar high-level purpose.

Do not assume Unix FIFO behavior and Windows named-pipe behavior are identical.

If software is platform-independent, define a platform-neutral IPC abstraction.

Implement platform-specific mechanisms behind it.

The externally visible semantics should remain consistent where required.

Unix domain sockets provide socket communication between processes on the same Unix-like system.

They can support:

Stream semantics.

Datagram semantics.

Local request-response.

Local services.

They avoid external network routing.

Filesystem-named Unix sockets can use filesystem permissions as part of access control.

Do not assume filesystem permissions alone provide all required authorization.

Peer credentials can sometimes be obtained through operating-system facilities.

Use them where appropriate.

Unix domain sockets can be useful when:

Processes are independently started.

Bidirectional communication is required.

Multiple clients connect to one local service.

A socket-style interface is convenient.

Do not use TCP localhost automatically when a local-domain socket better matches the requirement.

Likewise, do not use a Unix domain socket if cross-machine communication is required.

TCP sockets provide a reliable ordered byte stream between endpoints.

TCP can be used locally or across networks.

TCP does not provide application message boundaries.

Define framing.

TCP does not provide application identity merely because a connection exists.

Authentication may still be required.

TCP does not prove the peer is authorized.

Transport connectivity is not authority.

A TCP connection to:

127.0.0.1

is local network communication.

That can reduce exposure.

It does not automatically make every local client trusted.

Other processes running under other users may be able to connect depending on system configuration.

If the service performs privileged operations, authenticate or otherwise enforce the required local authority boundary.

Binding to all interfaces:

0.0.0.0

or:

::

can expose an IPC-style service to the network.

Do not change a local-only service to all-interface binding casually.

That changes the security boundary.

Configuration should make the binding explicit.

UDP provides datagram communication.

Datagrams preserve message boundaries.

UDP does not guarantee:

Delivery.

Ordering.

Uniqueness.

Connection establishment.

A UDP sender can send a datagram that never arrives.

Datagrams can arrive out of order.

Datagrams can be duplicated.

Applications using UDP must tolerate the behavior required by their protocol.

Do not build reliability assumptions into UDP merely because local testing rarely loses packets.

Local IPC can still use datagram sockets where their semantics are useful.

Choose based on required behavior.

Shared memory allows multiple processes to access a common memory region.

This can provide very high throughput.

It also introduces synchronization requirements.

Shared memory gives processes shared bytes.

It does not automatically provide:

Message boundaries.

Mutual exclusion.

Ordering.

Consistency.

Ownership.

Crash recovery.

A shared-memory structure needs a defined layout.

For example:

Header.

Version.

State.

Sequence number.

Data length.

Data.

Do not let separate processes independently assume structure layout without a stable contract.

Binary shared-memory structures can be affected by:

Alignment.

Padding.

Integer width.

Endianness.

Compiler ABI.

Structure packing.

Version differences.

Do not map an arbitrary native C struct into shared memory and assume every build will interpret it identically.

Define representation deliberately.

If all communicating processes use the same binary and platform, native layout can sometimes be acceptable.

Know the constraint.

If interoperability matters, use an explicitly defined representation.

Shared memory requires synchronization when multiple processes can access mutable data concurrently.

Possible mechanisms include:

Process-shared mutexes.

Semaphores.

Atomic operations.

Sequence locks.

Ring-buffer ownership rules.

Single-producer/single-consumer designs.

Do not access shared mutable data concurrently without a synchronization model.

Race conditions cross process boundaries just as they cross thread boundaries.

A shared-memory flag such as:

ready = 1

is not automatically sufficient synchronization.

Memory visibility and ordering matter.

Use synchronization primitives appropriate to the platform and language.

Do not invent a home-grown lock from ordinary integer reads and writes unless the required atomic and memory-order semantics are established.

Shared memory can outlive a process depending on the mechanism.

A crashed process can leave:

Stale objects.

Stale state.

Locks.

Partial records.

Ownership markers.

Recovery behavior must be defined.

Do not assume shared state is valid merely because the memory object still exists.

Version and validate persistent or semi-persistent shared structures.

A message queue communicates discrete messages.

This can simplify framing because the mechanism preserves message boundaries.

Message queues can provide:

Asynchronous communication.

Buffering.

Priority.

Multiple producers.

Multiple consumers.

The exact semantics depend on the queue implementation.

Do not assume all message queues guarantee the same behavior.

Determine:

Maximum message size.

Queue capacity.

Ordering.

Persistence.

Delivery guarantees.

Acknowledgement behavior.

Blocking behavior.

Failure behavior.

A full queue requires defined handling.

Possible policies include:

Block.

Wait with timeout.

Reject.

Drop according to explicit policy.

Apply backpressure.

Do not silently discard messages unless loss is an intentional property of the system.

Backpressure occurs when a producer generates work faster than a consumer can process it.

Without backpressure, queues can grow until memory or storage is exhausted.

Bound queues where appropriate.

When full, make behavior explicit.

Backpressure is part of IPC design.

Do not solve overload merely by making buffers enormous.

Large buffers delay failure.

They do not remove capacity limits.

Signals provide small asynchronous notifications to processes on Unix-like systems.

Examples include:

SIGTERM.

SIGINT.

SIGHUP.

SIGCHLD.

Signals are not general-purpose data transport.

Use them for events that fit signal semantics.

For example:

Request termination.

Notify configuration reload.

Notify child process state change.

Do not try to transmit large structured data through ordinary signals.

Signal handlers have severe restrictions in many environments.

Only async-signal-safe operations can safely be performed directly inside a POSIX signal handler.

Do not perform complex application logic inside the handler.

A common design is:

Signal handler sets a flag or writes to a safe notification mechanism.

Normal event loop observes the notification.

Normal code performs the work.

This keeps complex behavior out of asynchronous signal context.

Do not call arbitrary allocation, logging, or locking code from signal handlers unless the platform guarantees it is safe.

Signals can interrupt blocking operations.

System calls can return interruption errors.

Handle interruption according to API semantics.

Do not treat every interrupted call as permanent failure.

Likewise, do not retry blindly if cancellation or shutdown is intended.

Signals can be coalesced.

Do not assume one signal delivery corresponds exactly to one logical event unless the mechanism guarantees it.

If event counts matter, use a mechanism designed to preserve counts.

Semaphores provide synchronization and counting.

A semaphore can represent available resources or coordinate processes.

For example:

Producer adds an item.

Semaphore count increases.

Consumer waits.

Consumer removes an item.

Do not use a semaphore without defining what its count represents.

A binary semaphore can provide lock-like behavior.

A counting semaphore represents multiple available units.

Do not confuse semaphore state with application data.

The data still needs its own representation.

Mutexes can sometimes be shared between processes.

A process-shared mutex requires explicit platform support and correct initialization.

Do not assume a normal thread mutex automatically works across processes.

Crash behavior matters.

If a process dies while holding an inter-process mutex, other processes can deadlock depending on the mechanism.

Robust mutex facilities can help detect owner death.

Recovery still requires application logic.

A dead owner does not prove protected data is consistent.

The process could have died halfway through an update.

After detecting owner death:

Inspect or recover protected state.

Restore invariants.

Then continue if safe.

Do not simply unlock and assume everything is valid.

Memory-mapped files can provide shared or persistent communication.

Multiple processes can map the same file.

Changes can become visible according to mapping and synchronization semantics.

Memory-mapped files share many concerns with shared memory:

Layout.

Synchronization.

Partial updates.

Crash recovery.

Versioning.

File permissions.

Do not use memory mapping merely because it avoids explicit read and write calls.

It changes the programming model but does not remove consistency requirements.

Files themselves can be IPC.

One process writes a file.

Another reads it.

This can be perfectly appropriate.

For example:

Batch processing.

Drop directories.

Configuration generation.

Job handoff.

Export/import.

Do not dismiss file-based IPC as primitive.

It can be simple, inspectable, durable, and easy to debug.

But define ownership and atomicity.

A writer should not expose a partially written file as complete data.

A common pattern is:

Write temporary file.

Flush as required.

Close it.

Atomically rename into final location.

Reader only consumes final names.

This reduces partial-read races.

The exact atomicity guarantees depend on filesystem and platform.

Know them.

File-based IPC needs a way to detect new work.

Options include:

Polling.

Filesystem notifications.

Directory scanning.

Explicit notification through another IPC mechanism.

Polling can be sufficient for low-frequency work.

Do not introduce complex notification infrastructure if a five-second directory scan satisfies requirements.

Small and deterministic can beat clever.

If multiple processes consume files, define claiming semantics.

For example:

Atomic rename from pending to processing.

This can establish ownership.

Do not let two workers process the same file because both observed it before either marked it claimed.

IPC can be synchronous.

A synchronous request waits for a response.

For example:

Client sends request.

Server processes it.

Server returns response.

Client continues.

This is simple when operations are short and bounded.

Do not use unbounded synchronous waits.

Define timeouts or cancellation where required.

IPC can be asynchronous.

A sender submits a message and continues.

The result can arrive later.

This can improve decoupling.

It also introduces:

Correlation.

Queueing.

Retry.

Ordering.

Lifecycle.

Cancellation.

Do not choose asynchronous communication merely because it sounds scalable.

It adds state.

Use it when the problem requires it.

Request-response protocols need correlation when multiple requests can be outstanding.

For example:

request_id=42

Response:

request_id=42

Do not assume responses arrive in request order unless the protocol guarantees it.

Correlation identifiers should be unique within the required scope.

They do not need to be globally unique unless the protocol requires it.

A monotonically increasing local request number can be sufficient for one connection.

Do not introduce globally unique identifiers without need.

If identifiers can wrap, define behavior.

IPC messages should have explicit types.

For example:

STATUS_REQUEST

STATUS_RESPONSE

START_REQUEST

START_RESPONSE

ERROR_RESPONSE

Do not infer message type from vague payload contents if a type field can make the protocol explicit.

A message type does not authorize the operation.

The receiver still validates:

Connection state.

Sender identity where required.

Sender authority where required.

Message structure.

Message values.

Current application state.

A START_REQUEST received from an unauthorized process remains unauthorized.

IPC transports requests.

It does not grant authority.

IPC messages should be validated at the receiving boundary.

Never assume another local process always sends correct data.

Processes can have bugs.

Versions can differ.

Data can be corrupted.

A local process can be compromised.

Validate.

For every message validate:

Header.

Version.

Type.

Length.

Required fields.

Ranges.

Encoding.

Current protocol state.

Authorization where required.

Do not pass malformed IPC data deeper into the application.

Message size limits are essential.

Define maximum payload size.

Reject oversized messages before allocating excessive resources.

For example:

MAX_MESSAGE_SIZE = 1 MiB

If header says:

length = 4 GiB

reject it.

Do not attempt allocation first.

Length arithmetic must be checked for overflow.

For example:

total = header_size + payload_size

can overflow fixed-width integers.

Validate before arithmetic or use checked arithmetic.

IPC protocols need encoding rules.

Possible encodings include:

Binary.

JSON.

TSV.

Line-oriented text.

Length-prefixed text.

Protocol-specific structures.

Choose based on requirements.

Text protocols are often easier to inspect.

Binary protocols can be smaller and faster.

Neither is automatically better.

For small local control protocols, simple text can be entirely adequate.

Do not build a binary serialization framework to transmit three commands unless there is a reason.

TSV can be useful for simple deterministic records.

For example:

STATUS	42	RUNNING

Define:

Column count.

Column meaning.

Escaping.

Encoding.

Maximum field length.

Do not assume fields will never contain tabs unless the protocol prohibits them.

If tabs are prohibited, validate and reject them.

JSON can be useful for structured messages.

Validate JSON structure after parsing.

Valid JSON is not necessarily a valid protocol message.

For example:

{"type":"START","port":-1}

is valid JSON.

It can still be semantically invalid.

Parsing is not validation.

Binary protocols need byte order.

Multi-byte integers must have defined representation.

Network byte order is commonly big-endian for network protocols.

Local IPC can use another representation if explicitly defined.

Do not use native host byte order in an interoperable protocol unless all participants are guaranteed to share it and that dependency is intentional.

The protocol defines byte order.

A network does not independently invent byte order at runtime.

Protocol designers define representation.

Version IPC protocols when incompatible changes are possible.

A header can include:

magic.

version.

type.

length.

request identifier.

Do not add fields merely for decoration.

Each field should serve a purpose.

Magic values can help identify protocol data.

They do not provide security.

A matching magic number does not authenticate the sender.

Version negotiation can be useful when processes can run different software versions.

For example:

Client supports versions 1 and 2.

Server supports version 2.

They select version 2.

If no common version exists:

Reject the connection.

Do not guess.

For tightly coupled processes deployed together, explicit negotiation can be unnecessary.

A fixed protocol version can be simpler.

Know the deployment model.

Backward compatibility has cost.

Do not support old protocol versions forever without need.

When support is removed, fail clearly.

Do not reinterpret old messages as new messages based on guesswork.

IPC state machines define valid message sequences.

For example:

CONNECTED

HELLO_SENT

QUALIFIED

READY

CLOSING

A command received before READY can be rejected.

Do not process a valid command in an invalid protocol state.

Message validity includes sequence.

This directly applies the state-machine principle:

An event does not authorize an arbitrary transition.

Only a defined transition does.

IPC peers can disconnect at any time.

Handle:

Clean close.

Crash.

Timeout.

Broken pipe.

Connection reset.

Protocol error.

Local shutdown.

Do not assume a peer will always send a graceful goodbye.

Resources associated with a connection must be cleaned up.

Examples:

Buffers.

Pending requests.

Locks.

Temporary files.

Shared-memory ownership.

Subscriptions.

Do not leak resources because the peer disappeared unexpectedly.

A broken pipe is normal failure behavior in IPC systems.

Do not crash the entire process merely because one client disconnected unless architecture requires it.

On Unix-like systems, writing to a closed pipe or socket can generate SIGPIPE.

Programs should handle this according to design.

Possible approaches include:

Ignore SIGPIPE and handle the write error.

Use APIs or flags that suppress the signal.

Define another controlled behavior.

Do not let an ordinary client disconnect unexpectedly terminate a long-running server.

Timeouts need clear semantics.

Possible timeouts include:

Connection timeout.

Handshake timeout.

Read timeout.

Write timeout.

Request timeout.

Idle timeout.

Shutdown timeout.

Do not use one vague timeout value for everything unless identical semantics are intentional.

A request timeout means:

The requester stopped waiting.

It does not necessarily mean:

The remote operation did not occur.

This distinction is critical.

For example:

Client sends START.

Server performs START.

Response is lost.

Client times out.

Retrying START can duplicate the operation.

Use idempotency or request identifiers where duplication matters.

Timeout is uncertainty.

Do not automatically translate it into operation failure if the remote result is unknown.

IPC retries must consider side effects.

Safe retry:

STATUS request.

Potentially unsafe retry:

TRANSFER_FUNDS.

START_JOB.

DELETE_FILE.

If an operation is not naturally idempotent, use an operation identifier.

The server can remember:

request_id=42 already completed.

Then a duplicate request can return the prior result rather than repeating the action.

Do not rely on transport retries to provide application exactly-once semantics.

Exactly-once effects require application design.

At-most-once, at-least-once, and effectively-once behavior have different tradeoffs.

Define what the system needs.

Do not advertise stronger guarantees than the implementation provides.

Ordering matters.

A stream preserves byte order.

That does not automatically define semantic operation order across multiple connections.

If client A sends operation 1 and client B sends operation 2 concurrently, the server needs a defined ordering mechanism if order matters.

Possible mechanisms include:

Single event loop.

Queue.

Sequence numbers.

Locks.

Transactions.

Consensus for distributed systems.

IPC itself does not solve application ordering.

If messages have sequence numbers:

Validate them.

Detect duplicates where required.

Detect stale messages where required.

Do not accept arbitrary sequence jumps if protocol forbids them.

Sequence numbers can wrap.

Define comparison semantics if long-lived communication can reach wraparound.

IPC can cross privilege boundaries.

For example:

Unprivileged user process.

Privileged service.

This boundary requires special care.

Never trust a privileged operation request merely because it arrived through a local socket.

Authenticate the caller using an appropriate mechanism.

Authorize the requested operation.

Validate all parameters.

Apply least privilege.

Do not expose generic:

EXECUTE_COMMAND

interfaces from privileged services unless arbitrary execution is explicitly the intended feature.

Prefer narrow operations.

For example:

GET_STATUS

RELOAD_CONFIGURATION

START_SERVICE

STOP_SERVICE

Each can have explicit authorization.

Narrow IPC interfaces reduce attack surface.

A privileged service should not accept arbitrary filesystem paths without validation if the operation acts on those paths.

Path traversal and symlink attacks can cross IPC boundaries.

Treat IPC input like any other untrusted input.

Local does not mean safe.

Unix domain socket peer credentials can identify:

User ID.

Group ID.

Process ID.

Availability varies by platform.

Use operating-system-provided peer identity where appropriate rather than trusting a client-supplied field:

{"uid":0}

A client claiming to be root is not evidence.

Obtain identity from the trusted transport or authentication mechanism.

Named-pipe security descriptors on Windows can restrict access.

Unix filesystem permissions can restrict local socket or FIFO access.

These mechanisms can establish part of the access boundary.

Do not duplicate security poorly in application code when the operating system already provides a stronger primitive.

But understand exactly what the OS primitive guarantees.

Authentication answers:

Who is the peer?

Authorization answers:

What may the peer do?

Keep them separate.

IPC confidentiality may matter.

Local IPC can sometimes rely on operating-system isolation.

Network IPC can require encryption such as TLS.

Do not add encryption where it solves no threat in the defined environment merely for decoration.

Do not omit it where data crosses an untrusted network.

Threat model the actual transport.

Integrity matters even when confidentiality does not.

A message altered in transit can change behavior.

Transport and protocol mechanisms should provide the required integrity guarantees.

TCP checksums are not cryptographic integrity protection against an attacker.

Know the distinction.

IPC servers should limit clients.

Possible limits include:

Maximum simultaneous connections.

Maximum requests per connection.

Maximum message size.

Maximum queue depth.

Maximum pending requests.

Idle timeout.

Per-client resource limits.

Do not let one client consume unbounded server resources.

Resource exhaustion is an IPC concern.

A client can connect and send nothing.

If each connection consumes memory forever, enough idle clients can exhaust the server.

Use bounded resources and timeouts appropriate to the mission.

Rate limiting can be useful.

Do not add it automatically to tiny trusted local systems if connection limits already solve the problem.

Use the smallest sufficient mechanism.

IPC servers need shutdown behavior.

A graceful shutdown can:

Stop accepting new clients.

Notify existing clients where appropriate.

Finish or cancel active operations according to policy.

Flush required state.

Close IPC endpoints.

Release resources.

Exit.

Do not simply terminate halfway through a persistent state update unless abrupt termination semantics are acceptable.

Shutdown itself can be state-driven.

For example:

RUNNING

DRAINING

STOPPING

STOPPED

Do not accept new work in STOPPING unless defined.

Clients need reconnection behavior.

If a server restarts:

Can clients reconnect?

Do they retry automatically?

How often?

Do they resend pending requests?

Are those requests idempotent?

Do not implement reconnect without defining pending-operation behavior.

A reconnect creates a new transport session.

Do not assume it resumes old protocol state automatically.

Perform required handshake again.

Re-authenticate if required.

Re-establish subscriptions.

Do not carry stale connection state into a new connection.

Connection identity and application identity can differ.

A user or agent can reconnect through a new socket while retaining application identity.

Define the relationship.

Do not use ephemeral socket descriptors as durable identities.

File descriptors and handles are process-local resources.

The integer:

5

does not globally identify a connection.

Do not persist file descriptor numbers as durable references.

They can be reused.

IPC endpoint names should be stable where needed.

For example:

/run/digit/control.sock

Naming should communicate purpose.

Temporary runtime endpoints should live in appropriate runtime directories.

Do not place mutable sockets in configuration directories merely because the path is convenient.

Separate configuration from runtime state.

Runtime socket directories need correct permissions.

Do not create privileged sockets in world-writable locations without protections against substitution.

Temporary directories can introduce race conditions.

Use secure creation mechanisms.

If an IPC server creates a filesystem socket:

Handle stale socket files from prior crashes.

Do not blindly delete any file at that path.

Verify what it is and whether removal is safe.

An attacker could place a symlink or unrelated file there.

Filesystem security applies.

PID files are not IPC by themselves.

They can help locate or identify a process.

Do not trust a PID file as proof that the intended process is alive.

PIDs are reused.

If identity matters, verify the process through stronger evidence.

Signals sent using a stale PID can reach an unrelated process after PID reuse.

Use process handles or additional identity checks where available.

IPC and process supervision often interact.

A supervisor can:

Start child.

Capture stdout/stderr.

Monitor exit.

Restart according to policy.

Send termination.

This is a controlled parent-child relationship.

Do not create a separate network service if inherited pipes satisfy the requirement.

Simple process trees can be robust.

Subprocess IPC should avoid deadlocks.

A classic deadlock occurs when:

Parent writes large data to child stdin.

Child writes large data to stdout.

Both pipe buffers fill.

Each process waits for the other to read.

If bidirectional communication can be concurrent, design reads and writes accordingly.

Possible solutions include:

Separate threads.

Nonblocking I/O.

Event loops.

Bounded request-response sequencing.

Do not assume pipe buffers are infinite.

Pipe buffer sizes are implementation details.

Do not build correctness around a particular capacity.

A process can block while writing when the reader is slow.

That is backpressure.

Decide whether blocking is acceptable.

Nonblocking IPC returns when an operation cannot proceed immediately.

The program must then wait for readiness through mechanisms such as:

select.

poll.

epoll.

kqueue.

IOCP.

Other platform facilities.

Do not busy-loop:

while write fails:
    try again

That wastes CPU.

Wait for readiness or use blocking I/O where appropriate.

Blocking I/O is not inferior.

For simple single-purpose processes, blocking operations can be easiest to reason about.

Use nonblocking complexity when concurrency requirements justify it.

Event-driven IPC can handle many connections efficiently.

It also introduces state management.

Each connection can have:

Read buffer.

Write buffer.

Protocol state.

Pending requests.

Timeout.

Authentication state.

Do not adopt event-driven architecture without modeling these states explicitly.

Partial messages must remain buffered until complete.

Do not discard partial input merely because one event-loop iteration ended.

For example:

Maximum header size.

Maximum message size.

Maximum buffered incomplete data.

Handshake timeout.

Define limits.

Malformed peers should be disconnected according to protocol.

Do not attempt infinite recovery from arbitrary garbage.

Close connection.

Require a new handshake.

Do not scan arbitrary bytes looking for something that resembles a header unless the protocol explicitly defines resynchronization.

Fail deterministically.

Known request bytes.

Expected parsed fields.

Known response bytes.

Malformed length.

Unknown message type.

Unsupported version.

Cross-language IPC especially benefits from test vectors.
