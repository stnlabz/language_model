# build go — native Word GRU

The Operator-authorized language-learning replacement uses `word_gru.c`: an original, C11, word-token gated recurrent unit. It trains from the approved Digit JSONL converted into line-oriented lessons by `migrate.c` and partitioned into train/validation by `prepare.c`. No external pretrained weights, inference services or runtime dependencies are used.

Run `build go` in an MSVC Developer CMD. Existing `runs` content is deleted at the start of each run, and results are written to `runs\gru_run` only.

The training run creates `word_gru.stn` (the lowest-held-out-loss weight snapshot including training vocabulary), `word_gru.log`, and `best_sample.txt`. The sample comes from sampling the word GRU distribution; it is not a copied approved sentence or a hardcoded answer. `build go` displays the sample in CMD.

**Qualification boundary:** A successful build, decreasing word-token loss, or valid spelling does **not** prove coherent language. Inspect real generated sentences and classify incoherent output as FAIL. The checkpoint file format is incompatible with the historical byte-level `model.c` checkpoints. This experimental replacement does not change Digit, Ezra, other agents, or deployments.

## Word-order decoding (2026-10-21)

The word GRU retains learned next-word probabilities, but generation now restricts adjacent word choices to transitions actually observed in Digit's training split. Transition frequency and the GRU probability both influence sampling. Only the training split is used for these constraints. This reduces unsupported local word combinations but does not prove whole-sentence grammar, factuality, originality, or meaning. A generated sample must still be reviewed for coherence; an incoherent sample is a FAIL even if the process exits successfully.

## Supervised answer objective (2026-10-24)

Windows `build go` now passes the isolated, operator-approved `dialogue_corpus.txt` to `word_gru train` as an optional fifth training argument (after `SAMPLE`). The baseline language training continues to use `digit_train.bin` and `digit_valid.bin`, selecting its best held-out-loss checkpoint as before. The separate dialogue stage fine-tunes that best checkpoint with **one supervised pass through each genuine question/answer pair**. It does not duplicate records or invent answers.

The dialogue tokenizer keeps each `Question: … Answer: …` record together: question-mark punctuation does not reset the GRU between prompt and answer. Its predictive loss is **masked on question-side tokens**, and applied to answer words and the final end-of-record token. Earlier question-side recurrent states can influence answer prediction within the 24-token truncated backpropagation window. The optimizer's moments are reset before the separate objective. In `word_gru.log`, `dialogue_pairs_supervised` and `answer_tokens_supervised` record what actually participated.

This change deliberately preserves the existing checkpoint serialization, general word-level inference interface and agent-side Core/retrieval boundaries. The optional argument retains the prior four-file training invocation for other workflows. The current seven approved dialogues are still sparse; this is an implementation of a conditional objective, **not** proof of useful conversations. The best-validation-loss figure describes the base language checkpoint **before** supervised dialogue fine-tuning. Windows GO keeps `language_quality=NOT_VERIFIED` and prints production-decoder samples for operator review. No deployment or agent modification is authorized by `build go`.

### Prompt conditioning in inference

The word-GRU `sample` command now consumes the live prompt with the same Q/A context tokens used in supervised training: `question [prompt] answer [generated tokens]`. The trained checkpoint must therefore be used with the matching updated `word_gru` binary; existing checkpoint files remain readable without a serialization change, but generated behavior may differ even for old checkpoints. The sampler still uses model probabilities and never retrieves a memorized answer directly.

Windows GO first executes `word_gru test-dialogue`, a deterministic source-only fixture checking the Q/A boundary, answer loss positions, and rejection of missing or empty answers. Its result is written to `dialogue_fixture.log`; failure stops the run before training. This is a parser qualification fixture, not a language qualification test. The operational word GRU and checkpoint must be tested by the Operator on Windows before any decision to replace Digit's running language model.

## Word GRU Q/A conditioning and vocabulary correction (2026-10-24)

The live IRC trace `explain yourself → The same group.` confirmed that a returned string passed only structural acceptance, not semantic relevance. The original `word_gru.c` contained three separate learning/inference defects:

1. **Beginning-of-sequence state mismatch:** teacher-forced supervised examples begin by predicting `question` from the BOS state, then advance the state through `question`, question words, and `answer`. The production sampler formerly started with `question` without the BOS recurrent update. `prime_question()` now performs the complete training-equivalent conditioning sequence; a deterministic native fixture compares its hidden state against explicit teacher-forcing operations.
2. **Loss normalization and insufficient answer learning:** supervised dialogue used a single pass and scaled each optimizer update by *all* tokens in a BPTT chunk, even though only answer targets were supervised. The optimizer now normalizes by supervised targets, and the Q/A stage uses 24 measured passes through the same approved examples. `word_gru.log` includes `dialogue_epoch`, `dialogue_pairs_supervised`, `answer_tokens_supervised`, and `answer_train_loss` for each pass. Training-loss improvement **is not** held-out performance or a conversation qualification.
3. **Frequency-limited vocabulary erased genuine answers:** the fixed 2048-word dictionary previously selected words only from high-frequency language text. Approved but infrequent Q/A words and even the `question`/`answer` delimiters could become `<unk>`, making them impossible to predict as distinct words. The new vocabulary construction explicitly reserves both delimiters and every unique word in the approved dialogue corpus before filling remaining slots by language frequency. Capacity overflow fails visibly rather than silently truncating. `dialogue_vocabulary_reserved` records how many terms were preserved, and the native fixture verifies this contract.

Only original STN-Labz C code, existing approved training inputs, and the existing checkpoint format are used; no external weights, synthetic dialogue, remote model, automatic repair, or deployment is introduced. These training changes produce **different checkpoint vocabulary indices and weights** and therefore require an operator-controlled full retrain before using the corrected sampler. Older `WRG1` checkpoints remain readable at the file-format level, but the sampler now rejects checkpoints lacking actual `question`/`answer` terms rather than silently treating the markers as unknown. A rebuilt executable alone will not repair an older checkpoint.

**Limitations:** The observed approved set has only seven distinct genuine dialogue pairs. Repeated optimization can fit those pairs but cannot supply missing dialogue diversity, general-purpose reasoning, or guaranteed relevance for unseen questions. The Windows GO report must continue to state `LANGUAGE NOT QUALIFIED`. Only independent question/answer evaluation and operator acceptance can justify deployment. Execute Windows `build go` to run the native tokenizer/vocabulary/BOS fixture and review the complete training-loss history and live production-decoder outputs; these tests have not been run by the assistant.

## Checkpoint and decoder parity investigation (2026-10-24)

The operator reproduced two incoherent GRU responses directly on Linux using `./word_gru sample word_gru.stn ... 32 913 0.65 0`, which eliminates Digit/IRC as the source of those particular generated strings. Windows `build go` produced a different sampled output for `Digit, explain yourself`, but it is not yet established whether the Linux and Windows checkpoint **bytes** and sampler executables are equivalent. A fixed seed is insufficient proof of equivalent checkpoint contents or identical cross-platform floating-point sampling.

The native word-GRU executable now supports read-only diagnostics without creating, modifying, or loading a new model into Digit:

- `word_gru inspect CHECKPOINT` validates the existing checkpoint and prints `checkpoint_bytes`, `checkpoint_fnv1a64`, vocabulary size, and the IDs of `question`/`answer` markers. FNV-1a is only a convenient reproducibility fingerprint; compare `sha256sum` / `certutil -hashfile ... SHA256` for cryptographic file identity.
- `word_gru sample-greedy CHECKPOINT PROMPT WORDS SEED TEMPERATURE PENALTY` follows the **same** checkpoint, Q/A-state conditioning, vocabulary, and generation code as `sample` but selects the highest-probability eligible next token with stable vocabulary-index tie-breaking rather than drawing a random sample. This is **diagnostic**, not a new qualified production decoder. Small cross-platform floating-point differences can still change argmax only near ties.
- The established `sample` command and the production HTTP API defaults are unchanged.

For comparable tests, use the **exact prompt bytes** on both systems, including punctuation and trailing spaces. Run both `inspect` and `sample-greedy` against each environment's actual checkpoint, and compare normal `sample` output separately. If fingerprint or vocabulary IDs differ, the checkpoints are not byte-equivalent. If fingerprints match but greedy outputs differ, inspect native numeric implementations or build artifacts. If fingerprints and greedy outputs match but stochastic outputs differ, sampling arithmetic or decoding environment is a stronger suspect. If both paths remain incoherent on the same checkpoint, that is a model-language quality defect that cannot be repaired by changing a module loader.

## Dual-objective qualification probe (2026-10-24)

The human Operator authorized making the two required outcomes measurable, **not** another retraining run: (1) previously unseen conversational answer behavior, and (2) preservation of general-language performance.

The native `word_gru evaluate-checkpoint CHECKPOINT BASE_VALID TRAIN_DIALOGUE HELDOUT_DIALOGUE` command restores the exact saved checkpoint and **does not optimize, modify, or save weights**. It reports (a) teacher-forced next-token loss and unknown tokens on the original held-out general-language validation split, and (b) masked answer-token loss, number of Q/A pairs, and unknown answer tokens on an *operator-supplied*, distinct held-out Q/A corpus. Held-out lines that exactly match any of the supervised dialogue-training lines are rejected. That disjointness check is exact-line comparison, not a semantic-near-duplicate detector; the Operator must establish source provenance and remove paraphrastic overlap.

Linux invocation: `make evaluate HELDOUT_DIALOGUE=/path/to/approved_heldout_dialogue.txt`. Defaults are `CHECKPOINT=word_gru.stn`, `BASE_VALID=gru_run/gru_validation.bin`, and `TRAIN_DIALOGUE=gru_run/dialogue_corpus.txt`. The held-out file must use the already supported one-record-per-line `Question: ... Answer: ...` format and **must never have participated in vocabulary reservation, general/base text training, dialogue fine-tuning, or checkpoint selection**. Do not invent or derive examples from the approved Corpus/Context/Observation records. No held-out file is bundled or synthesized, and the Makefile fails closed when none is supplied. The existing source has seven genuine dialogue pairs, all already trained; **these cannot provide a valid unseen evaluation set for the current checkpoint**. Manually prepared, separately approved genuine exchanges are necessary.

The new command measures losses, **not** relevance, factuality, or naturalness. It explicitly reports `heldout_dialogue_semantic_relevance=NOT_EVALUATED`. A human-reviewed bank of unseen prompts and generated answers remains necessary to establish conversational generalization. To measure language preservation, compare the same base-validation set across pre-fine-tune and post-fine-tune checkpoints with identical vocabulary/tokenization; the current training log established post-fine-tune loss 4.93135 vs base selected 4.68370 (+0.24764). A candidate checkpoint must both demonstrate held-out conversational response quality **and** avoid unacceptable base validation regression; acceptable tolerances require Operator approval, not a hidden programmatic choice.

Changes: `word_gru.c` (native read-only evaluation command), `Makefile` (explicit opt-in evaluation target), `docs/BUILD_GO.md` (qualification protocol). ## Dialogue objective conflict: preservation-gated candidates (2026-10-24)

**Evidence motivating the experiment:** The operator's completed model fitted the seven approved dialogue pairs to answer training loss 0.581808, but answer loss on three disjoint held-out exchanges was 6.125849 (30 targets, 2 unknown tokens); full general-language held-out loss increased from 4.68370 to 4.931349 after fine-tuning. These show a reproducible trade-off, not a successful conversational model.

The native trainer now **retains a separate copy of the best pre-dialogue checkpoint** and fine-tunes a candidate copy. It evaluates complete base-language validation loss at dialogue epochs 1, 2, 4, 8, 12, 16, 20, and 24. A candidate may replace the retained model only if its base validation loss is finite and no more than 0.000001 above the pre-dialogue best. Among qualifying candidates it keeps the one with the lowest supervised dialogue training loss. This uses only the already existing base-validation partition and training dialogues; neither `helout.txt` nor any other held-out conversational answers are used for training or checkpoint selection. That preserves the distinction between model selection and independent conversational testing. This adds up to eight CPU validation scans to a new training run.

Training logs include `dialogue_candidate_epoch`, each candidate's `base_valid_loss`, `delta`, and `preservation` result, plus `dialogue_candidates_checked` and `accepted_epoch`. If every dialogue candidate worsens general-language validation, **the pre-dialogue base checkpoint is kept** and the log says `dialogue_checkpoint=BASE_RETAINED`. It does not falsely claim dialogue qualification or force an unqualified candidate into the saved checkpoint. The final checkpoint is still compared with the base validation and saved using the existing format; the existing checkpoint promotion and optional model runtime remain unchanged. A native `test-dialogue` fixture checks the preservation predicate against the operator's measured regression and non-finite loss. No new data, artificial dialogue, vocabulary, network dependency, or model architecture is introduced.

**Limitations:** Strict language preservation may reject all conversational candidates. A preserved base validation metric **does not imply** improved held-out conversations, and a lower seven-pair training loss does not establish generalization. The three held-out pairs remain the independent evaluation benchmark; use `make evaluate HELDOUT_DIALOGUE=helout.txt` only on a checkpoint the operator elects to test. No new Linux training was performed by the assistant; native compilation and candidate results await operator verification. Existing trained checkpoints are not modified by a source pull or test.
