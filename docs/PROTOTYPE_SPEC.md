# STN-Labz Native Language Model — Milestone 1 Prototype Specification

**Status:** APPROVED - PM 20261027:0233Z 
**Scope:** Specification only. No model code, training, deployment, Digit integration, Rictus integration, or data import is authorized by this document.

## 1. Objective

Define a small original trainable neural language model demonstrating measurable learning and basic generation from human-language data on the reported 2-vCPU, ~7.7-GiB RAM, CPU-only VPS. This is an experimental foundation for a future shared model used by Digit, Ezra, and potentially RictusD. It does not imply conversational fluency, engineering judgment, or operational authority.

## 2. Proposed implementation choices (not yet approved)

| Decision | Proposed prototype |
| --- | --- |
| Language | C11 with the standard C library and explicit source files; no model framework or external model |
| Text representation | UTF-8 input encoded as raw bytes, vocabulary 0–255; byte representation is not word understanding |
| Model | One-layer recurrent neural network with gated recurrent unit (GRU) and trainable 64-dimensional hidden state |
| Objective | Predict the next byte from prior bytes using cross-entropy |
| Training | Small batches, truncated backpropagation through time, deterministic fixed-seed initialization and shuffled training |
| Context window | 64 bytes per sequence initially |
| Parameter budget | Well under 1 million trainable parameters; exact count derived and recorded in implementation |
| Inference | Locally generate a bounded sequence from a provided text prefix using trained weights |
| Checkpoints | Explicit, versioned, documented local binary format with integrity checks; never include secrets |
| Dependencies | Compiler, standard C library, and approved operating-system facilities only |
| Agent integration | None at this milestone |

The byte-level GRU is a **candidate** for inexpensive experimentation, not a claim of advanced natural-language understanding or a final architecture for a fluent LLM. If the Operator prefers another initial model or source language, update this proposal before implementation.

## 3. Data constraints

- Start only with an explicitly authorized, provenance-known, UTF-8 plain-text training sample.
- Do **not** ingest Digit's reported ~50 MB Corpus or ~5 MB Observations by default.
- Do **not** ingest Context, agent policies, private records, credentials, system logs, or GitHub source as training data without material-specific authorization.
- Split approved data into train and held-out validation partitions without leakage. Record input checksums, filtering, split seed, and dataset version.
- Preserve source data; produce derived files only at an approved destination.
- Model training and Digit's on-demand data retrieval are separate functions.

## 4. CPU and operational limits (proposed)

- Target: at most one training CPU worker initially, leaving capacity for the existing VPS services.
- Default process memory budget: no more than 1 GiB resident memory; enforce a measured stop condition during testing.
- Avoid swap dependence, background daemons, and automatic startup.
- Bound all training sessions by an operator-selected maximum duration and explicit training-step limit.
- Stop cleanly on interruption; checkpoint only when the Operator authorizes an output directory.
- No production VPS job, remote operations, or integrations are included in this specification.

These budgets are proposed safety targets and have not been benchmarked.

## 5. Minimal external interface (future implementation contract proposal)

1. **Prepare** — validate authorized text, record provenance and deterministic train/validation split.
2. **Train** — accept explicit input paths, seed, step limit, memory/process constraints, and checkpoint destination.
3. **Evaluate** — calculate training and held-out average next-byte loss; compare with a simple frequency baseline.
4. **Generate** — accept explicit model checkpoint, prefix, output-length limit, and generation seed; emit generated bytes and diagnostics.

No network service, public API, agent integration, or interactive chat interface is proposed in the first prototype.

## 6. Acceptance tests (to be implemented and executed in later, separately authorized steps)

1. Invalid and missing inputs are rejected without modifying other files.
2. Training and validation are distinct and reproducible.
3. Identical configuration, data, and seed reproduce initial parameters and recorded results within the documented test environment.
4. The trained model's held-out loss improves against its initial untrained state on an approved learnable dataset.
5. The held-out score is compared with a documented simple baseline; lack of improvement is reported, not concealed.
6. Weights change through training, and model output is not a hardcoded response table.
7. Checkpoint save/load round-trip preserves predictions within documented numeric tolerance.
8. Generation is bounded by the requested limit and handles invalid bytes/inputs safely.
9. Resource consumption is recorded; a limit violation terminates without affecting running agents.
10. Negative tests cover corrupt checkpoint, invalid UTF-8 corpus policy, zero-length data, and unauthorized dataset paths.

Passing these tests would establish only the tested experimental capability. It would not establish human-like fluency, agent integration, qualification, or deployment acceptance.

## 7. Evidence and stop gates

- Engineering outputs will report source revision, source files changed, dependencies, compiled binary identity if applicable, test inputs, measured CPU/RAM/runtime, scores, and limitations.
- A model producing text is not proof of semantic understanding. Human-language fluency requires separate evaluation.
- The established MVC boundaries remain unchanged: routing, controllers, models/data, and views retain their respective duties.
- Policy and operational enforcement remain outside the language model's statistical predictions.
- Any later deployment to Digit's VPS, access to Corpus/Observations/Context, or modification of Digit or RictusD requires separate exact-scope Operator authorization.
- Stop after approved work and await Operator end-to-end evaluation, explicit acceptance, and authorization for the next named step.
